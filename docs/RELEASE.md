# Releasing tape

Tape ships from two upstreams, in parallel:

| Mirror | URL | Audience |
|--------|-----|----------|
| GitHub | `git@github.com:chenhg5/tape.git` | International / global; canonical npm + go-install origin |
| Gitee  | `git@gitee.com:cg33/tape.git`     | Mainland China; faster install + update for users behind throttled `github.com` |

`scripts/install.sh` and the `tape update` CLI both auto-select the
faster mirror at runtime (HEAD-probe race, ~1.5s budget). For that
to work, **every release must land on both hosts within a short
window** — otherwise CN users either get a stale `tape update` or
a 404 on the asset path.

This doc is the playbook for "I cut a tag, what do I have to do?".

## TL;DR

```bash
VERSION=0.1.0

# 1) cut the tag locally (signed if you have a GPG key)
git tag -s v$VERSION -m "tape v$VERSION"

# 2) push the tag to BOTH remotes
git push origin   v$VERSION    # github (canonical)
git push gitee    v$VERSION    # gitee mirror

# 3) build cross-platform binaries — both shapes:
#       raw binaries:    tape-{linux,darwin,windows}-{amd64,arm64}[.exe]
#         (install.sh's preferred path: one curl → chmod → mv;
#          no tar/unzip dep; Docker COPY-friendly)
#       bundled archives: tape_${VERSION}_{linux,darwin,windows}_{amd64,arm64}.{tar.gz,zip}
#         (binary + LICENSE + README; brew tap & manual downloaders)
scripts/release-binaries.sh $VERSION
#    → dist/release/tape-<os>-<arch>[.exe]                              (raw, 13-14M)
#    → dist/release/tape_${VERSION}_<os>_<arch>.{tar.gz,zip}            (bundled, ~6M)
#    → dist/release/*.sha256                                            (sidecars for both)
#    → dist/release/SHA256SUMS                                          (aggregate over everything)

# 4) GitHub release with the English notes from CHANGELOG.md
#    (heredoc keeps a single source of truth — the changelog —
#    instead of a parallel docs/release-notes/ tree that drifts.)
gh release create v$VERSION dist/release/* \
    --title "tape v$VERSION" \
    --notes "$(awk '/^## \[/{if(p)exit; if($0~/'$VERSION'/){p=1;next}} p' CHANGELOG.md)"

# 5) Gitee release with the Chinese notes (web UI; body comes from
#    the inline heredoc in step 5b below, copy-pasted).

# 6) npm publish (6 packages: 1 main + 5 platform sub-packages)
scripts/release-npm.sh $VERSION
# 6a) dry-run first if uncertain
NPM_DRY_RUN=1 scripts/release-npm.sh $VERSION
```

The `awk` snippet in step 4 extracts the body of the version's
`## [X.Y.Z]` section from CHANGELOG.md (everything between this
version's heading and the next `## [` line). Single source of
truth, no second markdown file to update, no drift.

For the Chinese Gitee notes (step 5), keep the body inline in
your release-day command — see the worked example below in the
"Gitee release notes (Chinese)" section. It's only ~50 lines of
Markdown and changes between releases, so a heredoc-in-shell is
strictly less work than a parallel file tree.

### Why these scripts are split

| Script | Output | Audience |
|--------|--------|----------|
| `scripts/release-binaries.sh` | tarballs + sha256 in `dist/release/` | `install.sh`, `tape update` (manual install method), homebrew tap users |
| `scripts/release-npm.sh` | 6 npm packages (1 main + 5 platform) | `npm install -g @tapeai/tape` users |

npm sub-packages already carry the prebuilt binary inside the
package tarball; there's no second download. So npm publish does
*not* depend on having the GitHub release assets up first — both
paths can run in parallel, or in either order.

## One-time setup

```bash
# Add the Gitee remote alongside origin (GitHub).
git remote add gitee git@gitee.com:cg33/tape.git
git remote -v        # confirm both
```

Pushing `--all` and `--tags` together is convenient but **noisy
on Gitee** (it tries to mirror every WIP branch). Push deliberately
instead:

```bash
git push origin main
git push gitee  main
```

A `git config alias.pushall '!git push origin && git push gitee'`
in `~/.gitconfig` makes "push to both" a one-liner without becoming
a global default.

## What needs to be on both hosts

| Asset | Where it must exist | Generated by |
|-------|---------------------|--------------|
| Source code at the tagged commit | both | `git push origin && git push gitee` |
| Release notes (English) | GitHub | inline `gh release create --notes` (sourced from CHANGELOG.md) |
| Release notes (Chinese) | Gitee | inline heredoc / paste into Gitee web UI |
| Raw binaries (`tape-<os>-<arch>[.exe]`) | both | `scripts/release-binaries.sh` |
| Bundled archives (`tape_<ver>_<os>_<arch>.{tar.gz,zip}`) | both | `scripts/release-binaries.sh` |
| Matching `.sha256` sidecars (for *both* shapes) | both | `scripts/release-binaries.sh` |
| Aggregate `SHA256SUMS` file | both (convenience) | `scripts/release-binaries.sh` |

The asset *names* must match byte-for-byte. `install.sh` derives
the URL from the running OS+arch and the resolved tag; if Gitee's
raw asset is called `tape_linux_amd64` instead of
`tape-linux-amd64`, the install falls back to the bundled archive
silently (still works, but a roundtrip slower for CN users on cold
download). Keep both naming conventions in lockstep with
`scripts/install.sh`.

### Uploading to Gitee

Gitee doesn't have an officially supported `gh release create`
equivalent in `git` itself. The two practical paths:

1. **Web UI** (one-off, manual):
   1. Visit `https://gitee.com/cg33/tape/releases/new`
   2. Pick the just-pushed tag (`v<ver>`)
   3. Title: `tape v<ver>`
   4. Body: paste the Chinese notes (see template below)
   5. Attach every file from `dist/release/`
2. **Gitee OpenAPI** (scriptable; requires a personal access token
   with `projects:write`). See
   https://gitee.com/api/v5/swagger#/postV5ReposOwnerRepoReleases.
   We don't ship a helper script yet — once we hit the cadence
   where the web UI gets old, we'll add `scripts/release-gitee.sh`
   that wraps the API.

### Gitee release notes (Chinese) template

Drop this body into the Gitee web UI's release body field, edit
the version number, and you're done. The English equivalent for
GitHub is generated from CHANGELOG.md via the awk one-liner in
step 4 of the TL;DR.

```markdown
# tape v0.1.0

首个公开版本。tape 把你和 12 款 AI 编码 agent 的会话归档、检索、复活——再不会因为 token 上限、换机器、换工具而丢光上下文。

## tape 是什么

你在跟 AI 编码 agent 协作(Claude Code、Codex、Cursor、Gemini CLI——目前支持 12 款)。会话越来越长,agent 撞到 token 上限;或者换了台机器;或者想换一款 agent 继续干同一件事——之前积累的上下文全没了。tape 解决的就是这件事:

    tape sync                                # 归档所有 agent 留下的会话
    tape ls                                  # 交互式浏览
    tape search "redis 连接池"               # 在所有历史会话里做全文检索
    tape restore <id> --to codex             # 把 Claude 的一段会话复活到 Codex
    tape export --split-by month             # 按月切片归档,方便备份

**所有数据只在本机**。tape 不会偷偷上报,不会在后台请求 GitHub 或 Gitee——更新检查必须主动触发。

## 主要特性

- **12 款 agent 全部只读**: Claude Code、Codex、Cursor、Gemini CLI、Antigravity、Qwen Code、iFlow、Qoder、Aider、OpenCode、MiMo Code、Kimi Code。每款都有 2 字母缩写(cc、cx、cs、ge……)
- **全文检索**: 基于 SQLite FTS5
- **跨 agent 会话复活**: 5 种策略(auto / native / memory / transcript / brief),Claude 的会话可以接到 Codex 继续聊
- **导出**: 单文件或按 size / agent / month 切片,zstd / gzip / xz / none 压缩,tar / zip 容器,`--jobs N` 并行编码
- **定时同步**: `tape sync --install --interval 1h`,Linux systemd timer / macOS LaunchAgent / Windows schtasks,不需要 root
- **远程同步**: `tape sync --remote user@host`,通过 SSH 拉远端机器的会话,自动打 host 标签
- **双镜像发版自动选最快**: GitHub 与 Gitee 双推,`tape update` 与 `install.sh` 自动 HEAD probe 选快的——**国内用户自动走 Gitee,零配置**
- **持久化默认值**: `tape config set defaults.exclude_agents cursor`,后续命令自动应用
- **操作历史**: `~/.tape/operations.log` 一行 JSONL,`tape history` 看
- **隐私优先**: 归档前自动剥除 token、API key、.env 值、SSH 私钥块

## 安装(国内推荐)

    # 用 Gitee 拉脚本,脚本本身还会自动 probe 选最快的镜像下二进制
    curl -fsSL https://gitee.com/cg33/tape/raw/main/scripts/install.sh | bash

    # 或者 npm + npmmirror
    npm install -g @tapeai/tape --registry=https://registry.npmmirror.com

    # 或者 Go 工具链 + goproxy.cn
    GOPROXY=https://goproxy.cn,direct go install github.com/chenhg5/tape/cmd/tape@v0.1.0

安装后跑一次 `tape sync`,把已有的会话全部归档。然后 `tape ls` / `tape search` 探索。

## 关于镜像

tape 同时维护 GitHub(chenhg5/tape) 与 Gitee(cg33/tape) 两个发布源,每次发版双推同样的二进制 + sha256。

    tape update -v               # 在 debug 输出里看两个站点的探测延迟
    tape update --mirror gitee   # 强制走 Gitee
    TAPE_MIRROR=gitee tape update  # 或者用环境变量锁定整个 shell

对于:
- **npm 用户**: 配 npmmirror.com,二进制随 npm 包下载,无需走 mirror 选择
- **go install 用户**: 配 `GOPROXY=https://goproxy.cn,direct`,由 Go module proxy 加速
- **install.sh 用户**: 脚本自身就有 mirror 探测

## 资产校验

每个文件附带 .sha256,聚合 SHA256SUMS 可以一把验全部:

    sha256sum -c SHA256SUMS

## 验证安装

    tape version --json | jq '.version, .commit, .install'
    tape update --check                  # 刚装完应该显示 up to date

完整变更列表见 [CHANGELOG.md](https://github.com/chenhg5/tape/blob/main/CHANGELOG.md)。
```

## npm + Go modules

These two distribution channels are **single-source** (GitHub only):

- **npm** (`@tapeai/tape`) pulls from `https://registry.npmjs.org`,
  which fetches from GitHub. We don't republish to a Gitee mirror
  registry — npm clients in CN typically use registry mirrors
  (e.g. `npmmirror.com`) that already cache the package.
- **Go modules** (`github.com/chenhg5/tape/cmd/tape`) pulls from
  the Go module proxy (`proxy.golang.org`). Mainland users typically
  set `GOPROXY=https://goproxy.cn,direct` which mirrors the same
  upstream.

So `tape update` for npm / go-install users doesn't go through the
mirror probe — the install method's own proxy story handles it.
The mirror probe matters specifically for **install.sh users**
(downloading a binary tarball) and for the **release metadata
fetch** (`tape update --check` hitting the API for a tag list).

## Verifying after release

```bash
# Did both shapes land on both mirrors with matching sha256?
# (raw binary — install.sh's preferred path)
diff <(curl -fsSL https://github.com/chenhg5/tape/releases/download/v0.2.0/tape-linux-amd64.sha256) \
     <(curl -fsSL https://gitee.com/cg33/tape/releases/download/v0.2.0/tape-linux-amd64.sha256)
# (bundled archive — fallback + brew tap path)
diff <(curl -fsSL https://github.com/chenhg5/tape/releases/download/v0.2.0/tape_0.2.0_linux_amd64.tar.gz.sha256) \
     <(curl -fsSL https://gitee.com/cg33/tape/releases/download/v0.2.0/tape_0.2.0_linux_amd64.tar.gz.sha256)

# Does `tape update --check` see the new tag from each mirror?
TAPE_MIRROR=github tape update --check --json | jq .latest
TAPE_MIRROR=gitee  tape update --check --json | jq .latest
```

Both should report the same `latest`. If Gitee lags, it's because
asset upload to Gitee is still in progress — wait a minute and
re-check, don't bypass.

## Hotfix policy

If a release is broken (bad binary, security CVE), **unpublish on
both** within the same change window:

```bash
gh release delete v0.2.0 --yes        # github
# Gitee: web UI → Releases → v0.2.0 → Delete
```

A half-deleted release where Gitee still serves the broken artifact
is worse than no release at all.
